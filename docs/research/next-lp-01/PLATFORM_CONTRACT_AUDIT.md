## Smallest prospective successor design

A future version may move the platform requirement to the real tool boundary,
without requiring a nonexistent reusable platform reference inside a grant.
That would be an explicit change to a new contract, not an interpretation that
makes the existing contract pass. Keep all frozen R1/R1-AV source and packages
unchanged.

1. Define a fresh versioned package and execution identity after independent
   review. Preserve scientific registration, exact original/effective source
   maps, owner scope/window, output custody, actual-volume review, no-retry,
   cleanup, resource and protected-volume gates.
2. Freeze the exact launcher operation: command/arguments, working directory,
   package and binding hashes, source/runtime identities, target resources,
   receipt source/destination and all dependent native/model effects. The
   supported approval request must disclose that complete scope and genuine
   owner provenance. Avoid broad reusable command-prefix approval.
3. Submit that actual operation through the supported tool boundary. A plan,
   schema or prepared request has status **approval not established**. The
   platform decides whether it can execute. Any denial remains binding; use
   only the supported review/override path while original deadlines hold, or
   stop. Do not replace tools, policies, writers or paths to obtain the effect.
4. Inside an approved invocation, enforce ordinary package/source/custody/time
   gates again immediately before enabling dependent effects. Bind the checked
   bytes to the actual imported/executed bytes and pin executable, arguments,
   environment, runtime and destinations. Review mutable paths, module shadowing,
   symlinks, receipt replacement, concurrent writers and deferred dispatch for
   check/use gaps. Source hashes stated in a request alone are insufficient.
5. Keep platform decision provenance in its genuine external tool/transcript
   context when available. Do not invent a durable reference or claim the
   process has verified one. The runtime must not accept `approved=True`, an
   environment marker, arbitrary JSON, a callback returning success or its own
   successful start as proof of platform authority. If a future supported issuer
   exposes verifiable evidence, add only its documented exact-action validation
   in a separately reviewed adapter.

The change concerns the absence of a durable platform-evidence prerequisite in a
new contract; it does **not** remove the supported execution gate. In this design
platform enforcement is external to the process, while the process validates
its scientific and custody inputs. Neither layer may impersonate the other.
A long-running controller must not treat approval of a preparatory command as
approval of later undisclosed dispatches; the precise operation and its complete
dependent effects must actually have reached the supported boundary. If that
cannot be established for the intended launcher, retain the blocker.
