# Mem0 OSS 2.2.1

## Role in MemLife-NLIP

Mem0 is the first real memory provider behind the provider-independent Phase 01
adapter contract. Phase 02A characterizes local lifecycle plumbing only. It does
not implement the Memory Authority Gateway, run attacks, make security claims,
or use a downstream decision model.

## Installation

Provider dependencies are isolated in `requirements/providers/mem0.txt`:

```text
mem0ai==2.2.1
sentence-transformers==6.1.0
```

`sentence-transformers` is the narrow dependency required by the installed
`mem0.embeddings.huggingface.HuggingFaceEmbedding` import path. No broad Mem0
extras bundle was installed. `pip show` reported Mem0 2.2.1 and
sentence-transformers 6.1.0; `pip check` reported no broken requirements.

## Runtime Components

- Mem0 OSS `Memory`, not hosted `MemoryClient`
- Embedded Qdrant from `qdrant-client`
- Local Hugging Face sentence-transformer embeddings
- SQLite native Mem0 history
- A constructed but unused OpenAI-compatible LLM object pointed at an unused
  loopback endpoint

No Mem0 cloud account or hosted platform API is used.

## Local Configuration

The adapter sets supported process configuration before importing Mem0:

- `MEM0_TELEMETRY=false`
- `MEM0_DIR=runtime/providers/mem0/scratch`
- `HF_HOME=runtime/model_cache/huggingface`
- `SENTENCE_TRANSFORMERS_HOME=runtime/model_cache/huggingface`

All writes call `Memory.add(..., infer=False)`. The placeholder LLM credential is
non-secret and is excluded from manifests. Its base URL is loopback-only so an
unexpected inference call cannot reach a paid external API. Integration tests
also replace `generate_response` with a fail-fast test hook during write paths.

## Adapter Mapping

| MemLife operation | Mem0 native operation |
| --- | --- |
| `reset_namespace` | `delete_all(user_id=namespace)` |
| `write` | `add(text, user_id=namespace, infer=False)` |
| `query` | `search(query, filters={"user_id": namespace})` |
| `update_or_supersede` | `update(memory_id, text=...)` |
| `delete_or_invalidate` | `delete(memory_id)` |
| `list_or_inspect` | `get_all(filters={"user_id": namespace})` |
| `restart` | close SQLite/Qdrant handles and reconstruct `Memory` |

## Native Capabilities

The adapter declares reset, write, query, native update, native delete, current
record inspection, and reconstruction as supported. Namespace isolation maps to
synthetic Mem0 `user_id` values. The reusable Phase 01 lifecycle smoke workflow
passed against the real provider.

## Unsupported / Non-Equivalent Semantics

Mem0 native update changes the current content under the same memory UUID. It
does not expose the Phase 01 reference provider's separate v1/v2 IDs or a native
`SUPERSEDED_BY` relationship. The adapter therefore reports an updated record
with the same ID and does not fabricate supersession metadata.

The tested Mem0 delete path is deletion, not revocation. A normalized
`REVOKED` request is rejected as unsupported. `get_all` exposes current records
only; the adapter does not manufacture deleted tombstones.

## Write Behavior

With `infer=False`, each synthetic string was stored directly as one memory.
Mem0 returned a UUID and created an `ADD` history event. The LLM fail-fast hook
recorded zero calls.

## Search Behavior

Dense semantic search with the local 384-dimensional
`paraphrase-MiniLM-L3-v2` model retrieved both the initial Cedar memory and its
updated content. User namespaces remained isolated through the `user_id` filter.

`fastembed` was intentionally not installed, so Mem0 logged that optional Qdrant
BM25 keyword scoring was disabled. Required dense search still passed. spaCy
extras were also absent; Mem0 used its fallback after logging lemmatization
warnings.

## Update Behavior

`Memory.update(memory_id, text=...)` retained the original UUID and replaced the
current stored text. Search and `get_all` returned only the updated Bob text.
SQLite history appended an `UPDATE` event with the Alice text in `old_memory`
and the Bob text in `new_memory`.

## Delete Behavior

`Memory.delete(memory_id)` removed the current memory from Qdrant. Subsequent
search and `get_all` returned no record for that namespace. The adapter returns
a normalized `DELETED` operation result but does not store a synthetic tombstone.

## History / Inspection Behavior

Before deletion, native `Memory.history(id)` returned `ADD` and `UPDATE` events.
After deletion it also returned a `DELETE` event containing the last text as
`old_memory`, `new_memory=null`, and `is_deleted=true`. Normal inspection
continued to show only current Qdrant records.

## Restart Behavior

A synthetic canary remained searchable after the adapter closed its SQLite and
Qdrant handles and reconstructed `Memory` with identical paths. After native
deletion and a second reconstruction, the canary remained absent from normal
search. SQLite delete history also remained observable. This is a bring-up
sanity result, not the final deletion-durability benchmark.

## Offline / External-Network Policy

Telemetry is disabled with Mem0's `MEM0_TELEMETRY=false` environment mechanism,
which also suppresses OSS notice fetching. The small embedding model was
downloaded once into the gitignored project cache. Tier 2 tests then set
`HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1` and completed from local files.
No LLM request, paid API, Mem0 hosted API, Docker service, Ollama process, or
Jetstream resource was used.

## Known Limitations

- Validated on local Windows/Python 3.14.3 and Jetstream Ubuntu/Python 3.12.3.
- Initial model provisioning requires a one-time Hugging Face download.
- Optional BM25 and spaCy NLP extras are not installed.
- Mem0's in-place update is not lifecycle supersession.
- Native history is provider-specific and is not exposed as current memories.
- No concurrency, performance, attack, or authorization behavior was tested.

## Jetstream2 Phase 02B Validation

The first managed attempt reached model acquisition but stopped before tests
because the remote `.venv` lacked `pytest`; its temporary floating IP was
deleted and the VM was shelved. The authorized retry installed the pinned core
requirements first and completed successfully on exact commit `813a32a`.

Live `findmnt /dev/sdb` resolved the ext4 volume at
`/media/volume/jisheng3_volume`. Provider state lived under
`memlife/providers/mem0/phase-02b`, while pip, Hugging Face, and torch caches
remained under `memlife/model_cache`. The stale `/media/volume/sdb` path was not
used.

Remote versions were Mem0 2.2.1, sentence-transformers 6.1.0, CPU-only torch
2.7.1+cpu, and qdrant-client 1.19.1. No installed `nvidia-*` packages were
present. Remote unit/contract tests reported `32 passed`; Mem0 integration
reported `3 passed`.

The Cedar lifecycle matched Phase 02A: write exposed `ADD`, query retrieved v1,
reconstruction preserved the write, update retained the UUID and exposed
`UPDATE`, delete removed the current record from query/list and exposed
`DELETE` with `is_deleted=true`, and post-delete reconstruction kept the value
absent while history remained visible.

The retry's managed finalizer deleted its temporary floating IP and returned
the VM to `SHELVED`. See `manifests/phase-02b-mem0-jetstream.json` and
`docs/phases/PHASE_02B_MEM0_JETSTREAM.md` for exact measured facts and the
Phase 02A comparison. These portability results do not constitute a security
evaluation or universal deletion-durability claim.
